# 行程审查与优化

## 何时使用
用户提供了已经安排好的行程(城市 + 日期 + 逐日景点/活动),要求评估合理性、优化或排查问题。
不适用:从零规划行程(走 default);单点问路(走问路工作流)。

## 输入识别(开始前必须完成)
从用户消息中提取:
- 城市
- 出行日期(或天数)
- 逐日安排(哪天去哪些地方、是否给出交通方式)
任何一项缺失且无法从上下文/用户信息推断 → 先反问,一次只问一个。禁止凭空补全景点或日期。

## 审查步骤(按顺序执行)

### 1. 结构检查(不调用工具)
- 每天安排 > 4 个景点/活动 → 记「过密」
- 同日两个安排看起来距离过远 → 进入第 2 步用工具核实
- 同一景点重复出现 → 记「重复」

### 2. 地理核查(调用 query_route)
- 对每天相邻的两个安排,查询公共交通/步行时长
- 城市编码使用行程城市(用户信息中的城市编码)
- 单段公共交通 > 60 分钟 → 记「跨区」,说明耗时并给出调序建议
- 只核查相邻且明确的地点;不臆造地址

### 3. 天气核查(调用 get_weather_info)
- 查询行程日的天气
- 雨天/高温/大风 → 该日户外安排标记「天气风险」,给出调整建议(换室内或调换日期)

### 4. 攻略核查(调用 search_travel_guide)
- 检索行程城市攻略,核对景点的建议游玩时长、门票、预约要求(仅限攻略实际提到的)
- 用户安排与攻略建议明显不符(如攻略建议半天,安排 1 小时)→ 记「时长不足」
- 攻略未提及的信息不得编造

### 5. 输出审查报告
固定结构:
1. 总结论:合理 / 发现 N 个风险点
2. 逐日问题清单,每条格式:第 X 天「安排」— 问题类别 — 依据 — 建议
3. 优化建议:调序 / 替换 / 减少

## 硬性要求
- 时间、票价、距离、开放时间等数字必须原样来自工具结果,不得改写、换算或四舍五入
- 没有工具数据支撑的判断只能作为常识性建议,不得写成事实
- 行程整体合理时必须明确说"合理",禁止为了找问题而编造风险
- 问题清单用列表,简洁;不得整段复制工具返回原文
